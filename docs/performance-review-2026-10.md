# Производительность: 9 октября 2026

Кандидат: 0.2.112. Проверка относится к рабочей копии и локальной архивной базе; публичный сервер не перезапускался. Исходные пользовательские изменения сохранены. Художественная схема архитектуры выполняется в отдельном чате, здесь — исполнение и производительность.

## Подтверждённые механизмы

| Участок | Проблема в коде | Изменение |
|---|---|---|
| UI рынка основ | Завершённый результат из `baseMarketCache` мог бессрочно предотвращать следующий GET, хотя сохранённые цены уже изменились | Автоопрос снова читает сохранённый endpoint; текущая таблица остаётся видимой во время запроса |
| Конкурирующие запросы UI | `refresh` входил в идентичность запроса; фоновый опрос мог отменить принудительный запрос с теми же фильтрами | Идентичность строится по фильтрам; смена фильтра отменяет старый запрос, поздний ответ игнорируется |
| Общая очередь trade2 | Ожидание cooldown удерживало глобальный lock и задерживало готовый другой маршрут | Сон вынесен за lock, срок повторно проверяется перед запросом; сами HTTP-запросы остаются последовательными |
| График предмета | Загружались строки всей категории за последние N снимков, затем Python отбирал один предмет | SQL выбирает прежнее окно меток категории, затем строки нужного предмета и метаданные снимка |
| История SQLite | Индексы по отдельным полям плохо соответствовали фильтрам категории и предмета | Добавлены индексы `(league, category, target, status, timestamp)` и `(league, category, target, status, item_id, timestamp)` |
| Обход каталога | После 429 заново строился batch с приоритетными перепроверками; обычная очередь могла не продвигаться, курсор терялся при перезапуске | Версионная контрольная точка SQLite хранит курсор, незавершённые основы и `retry_at`; после паузы сначала продолжается сохранённая очередь, ограниченная основа переносится в её конец |
| Владение заданием | Проверка возраста могла заменить всё ещё работающую coroutine | Живая задача сохраняет владение независимо от TTL; устаревший исполнитель не публикует результат и контрольную точку нового владельца |

Эти дефекты воспроизводятся по коду и изолированным тестам. Они объясняют возможную задержку и устаревшее отображение, но не доказывают причину каждого прежнего таймаута публичного сайта: доступные локальные серверные логи относятся к маю–июню и не содержат нужной трассировки текущего инцидента.

## Цена и ограничения

Дополнительно проверено объединение контрольной точки на синтетических 2000 строках и 60 обновлениях. Промежуточная реализация требовала 7,194 с из-за повторной нормализации всех предыдущих строк; итоговый проход по ключам — 0,0078 с при равном результате. Объединение выполняется один раз на сохранение. Это тест локальной обработки, без времени записи SQLite и без сетевых запросов; новая регрессионная проверка считает вызовы нормализации вместо нестабильного ограничения wall-clock времени.

- Два индекса увеличивают размер SQLite и стоимость записи. Первое создание на большой базе занимает время; миграция проверена на временной базе и идемпотентна. Перед производственным обновлением нужен штатный backup и окно первого запуска.
- Контрольная точка обхода привязана к лиге, валюте, статусу и параметру уровня; изменение состава или порядка каталога инвалидирует очередь. Срок хранения — 30 дней в существующем cache. Ошибка записи cache не останавливает сбор, но тогда восстановление после перезапуска не гарантируется.
- Лимитер сохраняет последовательные HTTP-запросы. Медленный активный запрос по-прежнему задерживает следующие: это не обещание устранения всех сетевых таймаутов.
- HTTPX разделяет connect/read/write/pool timeouts; они не задают общий срок всей операции с несколькими запросами и повторами. Для дальнейшей диагностики полезны отдельные метрики очереди, сети и обработки. [Документация HTTPX](https://www.python-httpx.org/advanced/timeouts/).
- WAL не включался автоматически: он меняет эксплуатационные требования, требует общей машины для процессов и управления checkpoint. [Документация SQLite](https://www.sqlite.org/wal.html).
- Сборщик и UI сохраняют разные роли: UI читает сохранённые данные; внешние обновления выполняет сборщик либо явное действие пользователя. При масштабировании нужен один владелец очереди сбора; запуск дополнительных web workers сам по себе не ускоряет безопасный обход рынка.
